先说结论里最要紧的：仓库有一枚定时炸弹

P0keystore-20261005/ 位于仓库根目录，且未被任何 gitignore 规则覆盖。

该目录在磁盘上包含 app-release-new.jks、cert.pem、key.pem 以及一份 凭据备忘-20261005.txt（.store-pw.txt 为空）。我用 git check-ignore 验证过：这些文件当前都不在忽略列表里。

关键在于规则的作用域——美股监控/.gitignore 里确实写了 *.jks、android/signing/，但那些规则只对该子目录生效，而 keystore 放在根目录，不在其管辖范围内。同理，backup-main-20261005.bundle（675 KB 全量备份包）和 .workbuddy/ 也都在未忽略状态。

你的仓库是公开的（5777-wq/openfinlens）。一次 git add . 就足以把 Android 签名私钥、证书私钥和口令备忘推上去，且泄露后无法靠改历史彻底撤回（GitHub 对已推送的密钥有吊销扫描，但那是事后补救）。

修复：在根 .gitignore 追加 keystore-*/、*.jks、*.keystore、*.pem、backup-*.bundle、.workbuddy/，然后用 git status --porcelain 确认这些路径不再出现。若签名口令已在别处复用，建议轮换。

P0本地落后远端 158 个提交，而第二产品完全不在版本控制里。

我先核实了一个可疑信号：data/ 下各文件的最后提交停在 2026-09-21，看起来像采集管线死了 16 天。但这是错的——我拉了线上部署的数据文件，generatedAt 是 2026-10-07T09:10:53Z，就在几小时前。管线是健康的，是你的本地工作副本没同步。

实测：git rev-list --left-right --count origin/main...HEAD → 158 0。158 个提交全部是机器人数据刷新（events / 13f / polymarket），且 main 分支没有配置 upstream 跟踪（git status -sb 只显示 ## main）。

与此同时，美股监控/ 整个目录处于未跟踪状态——它不是一个脚本片段，而是一个完整产品：PWA、Cloudflare Pages、签名 APK、4 条 GitHub Actions 工作流、PWA 离线壳、外加一个 skill/ 包。

风险叠加：无 upstream + 158 个远端提交 + 大量未跟踪新文件。这三者任意两个凑在一起，就会产出一场难收拾的合并事故。建议顺序：先补 ignore 规则 → 再决定美股监控是入库还是移出仓库 → 最后才 git pull --rebase。

产品判断：你有两个产品，但只有一个有复访理由

这是本次评审最核心的观点。把两个项目并排放，功能密度的差异其实暴露了产品定位的差异。

P1Meridian 才是有 PM 问题的产品，OpenFinLens 还没有。

差别不在代码质量——两者都很高。差别在「用户为什么明天还会回来」。Meridian 有：定时任务、推送通知、周线级别的第二套时间框架、自选清单、持仓隐私分层。这是一条被设计出来的习惯回路。

OpenFinLens 有 10 个 tab、5000+ 热力图、事件地图、13F、产业链、世界银行宏观——工程含量极高，但这些功能共享同一个复访缺口：没有一个功能是「非看不可」的。用户不会因为「今天有个新产业链环节强度变高了」而每天打开看板。

产品决策建议：明确写下「OpenFinLens 是我的主航道，还是我的技术资产库？」如果是前者，它需要一个像 Meridian 那样的每日触发器（比如收盘后的固定推送：「你的自选今天动了 3 个，回归信号 2 个」）；如果是后者，就把 Meridian 扶为主产品，看板转为它的数据层与展示层。两个产品各投入一半注意力的状态，对一个人来说等于两个都做不到 PM 级。

你没有任何数据能回答「有人在用吗」

P1产品侧埋点、反馈入口、Issue 模板——一个都没有。

我在 index.html 与 js/app.js 中检索 analytics / umami / plausible / gtag / clarity / feedback / sentry，零命中；.github/ 下只有 3 条工作流，没有 ISSUE_TEMPLATE。

这里有一个值得正视的矛盾：docs/ARCHITECTURE.md §15 把「无账号、无追踪」写成了产品原则。保护用户隐私当然对，但这条原则不应该被扩大解释成「不做任何度量」——两者是完全不同的东西。你的前端已经做了移动端适配、hash 深链、四套皮肤、键盘切 tab，这些投入没有一项能被验证是否有效。

最小可行闭环（半天工作量）：不追踪个人、只做聚合计数——统计各 tab 停留时长占比、页面日活、复访率；README 末尾放一个「用得怎么样」的反馈链接；建一个只有一页的 ISSUE_TEMPLATE。只要三个数，你就知道下一刀该砍在哪里。

测试信号是混的，导致「红了」没有信息量

P220 组测试中有 4 组依赖实网，README 的绿色徽章因此不可复现。

我在本机跑 node _test/run-all.mjs：4 组未通过——history(1) / breadth(2) / boards(2) / live(2)。逐条看失败原因，绝大多数是 fetch failed（我的执行环境连不上腾讯/东财），还有一条是 SPMO 上市日断言（实际 2015-10-30，预期 2015-10-01）。

诚实说明：这些失败大概率是环境与上游数据漂移，不是我证明了你的代码有 bug。我也无法在此环境下验证 README 上「20 组 250 条断言」的说法。

但设计问题是真的：纯函数测试（engine / compare / worldmap / technical 等）全部通过，说明离线层设计得很好；可一旦实网断言混进同一个 run-all，红绿就无法区分「我们改坏了」和「上游变了 / 网断了」。

修复：run-all 默认只跑离线组并全绿；实网组放到 --live 开关下，失败时降级为 warn 而非 fail；像 SPMO 上市日这类会随上游变的期望值，改成「断言合理性区间」而不是硬编码单日。

复检补记（2026-10-07 当日晚间）

更正「美股监控完全不在版本控制里」是误判。

复检发现 美股监控/ 自带完整 .git，是独立仓库 5777-wq/us-stock-monitor（公开，112+ 提交，本地与远端同步）。原评审只看了外层 openfinlens 仓库的 git status，嵌套仓库被显示为一个未跟踪目录，据此得出「未入库」结论——正确结论是：它早已独立成库，「收编」问题不存在，只需在外层 .gitignore 加一行防止误 gitlink（已加）。

新发现us-stock-monitor 的公开历史里留有旧签名密钥 + 明文口令。

android/signing/app.keystore 与 android/app/build.gradle 中的明文口令（storePassword/keyPassword = usmon2026）自 2026-10-01 提交进入公开历史；10-05 的 f69a431 做了轮换并从工作区删除，但删除不入史，任何人 clone 仍可从历史取回密钥和口令。

缓解因素（已逐项实测）：签名密钥已于 10-05 轮换，新口令为强随机串且未复用旧口令；新凭据只存于 GitHub Secrets 与仓库外备忘；usmon2026 在两个仓库的当前树与全部工作文件中均已无踪迹。

残余风险：持有旧密钥者可给 10-01～10-05 期间安装旧签名 APK 的设备推送恶意「更新」；个人产品实际暴露面接近于零。真正要紧的遗留动作：确认 usmon2026 没有在其他账号或服务中被复用（这点只能在仓库外排查）。

可选的卫生动作（非紧急）：用 git filter-repo 清除历史中的 keystore 与口令行并强推。由于密钥已轮换且内容可能早已被缓存，此动作属卫生性质而非止损性质。
